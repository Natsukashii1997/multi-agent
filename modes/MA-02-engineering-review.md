## 1. 目标

让实现者以外的一方判断「这次改动能不能被接受」：发现作者漏掉的逻辑、边界和回归风险，并且**在问题解决时结束**，不无限往返。要消除的单 Agent 风险：作者盲区；以及工程接力的两种老毛病：审到第 5 轮还在原地打转、拆单续审绕开计数。

审查是否完成由 ChatGPT 判断；审查事实由持久的问题台账承载；能不能继续自动往返由驿窗按硬规则执行。五轮内每一轮有价值就继续，没价值就停，到上限必须交还常浩。

## 2. 适用 / 禁用

- 适用：L1 及以上的代码、脚本、配置改动，已有 PR 和自测证据。
- 禁用：
  - L0（不改变代码行为的管理文档、记账类改动）：只做机械检查，不送审（agent-kit《工程流程》第 8 节第 3 条）；
  - 方向问题（问题定义、路线、架构前提）→ 转 [MA-01](MA-01-thinking-review.md)；
  - 只缺可运行证据、不缺判断 → 先补测试（或等 MA-03 成立后转 MA-03），不靠多审一轮补证据。
- 与 MA-03（候选）的分界：MA-02 回答「能不能接受」，产出审查意见和接受/升级决定；MA-03 回答「关键行为有没有被独立证实」，产出可复现的运行证据。MA-02 可以调用独立验证作为证据，但不默认绑定 Codex。
- MA-01 思维评审只共用第 5.5 节的上限与机械控制（上限、两种计数、格式补一次、通过通知），不套用问题台账和 P0/P1，出口仍按 MA-01。

## 4. 输入与交接物（接口）

- 送审前先定风险级（L0–L3，定义沿用 DT-ORC ARCHITECTURE 的风险分级），写进送审包第一行，并在调用 `relay_to_chatgpt` 时填 `risk`（L1–L3；L0 驿窗拒收）。风险级决定审查要求（第 5.1 节），不再决定轮数。
- 送审包：驿窗「六项」，即任务名与目标、改了什么和为什么、分支与 PR 链接、diff 或摘要、希望重点看哪里、按严重程度列问题。另外要绑定 `repo / base_sha / head_sha`；被审的 PR 链接要是送审包里第一个出现的 PR 链接，同一验收目标拆单、换 PR 时要写明原单（第 5.4 节）。
- 第 2 轮起，送审包还要有：**本轮目的**（这轮修了什么、改了什么、要验证什么）、**上一轮台账**（驿窗带入，Claude 逐条写处理：已修并附证据 / 提议判定不成立并附反证 / 提议转单）。
- 回信：按严重程度（P0–P3）列问题，并给出更新后的问题台账（第 5.2 节）。P0/P1 必须写失败路径、违反的约束或风险依据；写不出的按 P2 及以下处理。回信最后四行：

  ```
  受审版本：<实际审过的 commit SHA>
  未决：P0 n，P1 n
  审查出口：通过 / 返修 / 证据不足暂停 / 决策升级
  结论：通过 / 需修改
  ```

  - 审查出口四档（第 5.3 节）；「通过」配「结论：通过」，其余配「结论：需修改」。驿窗结论仍是二态，四档写在倒数第二行。
  - 「未决」只用于展示和统计，不控制停机；写了「未决 0」也不能代替审查出口。
  - 受审版本和送审包的 `head_sha` 对不上：驿窗不按通过放行，停下交还常浩。
  - 末尾几行缺字段、值认不出、出口与结论对不上：驿窗先自动请 ChatGPT 只补一次格式（不计轮），还不对才停下交还常浩。

## 5. 审核门与停止条件（常浩 2026-11-14 裁决，取代 2026-11-07 的按级预算）

### 5.1 风险级只定审查要求

| 级别 | 送审 | 额外要求 |
|---|---|---|
| L0 | 不送审 | 机械检查 |
| L1 | 送审 | 自测和增量证据。只剩 P2/P3 时按「通过附建议」收口；有 P0/P1 时，改完必须复核一轮，不能「补改未复审」 |
| L2 | 送审 | 自测、回归与独立主审 |
| L3 | 送审 | 前置风险分析、必要的独立验证、常浩动作授权 |

所有级别共用同一个上限（第 5.5 节）；实际审几轮由第 5.3 节的审核门决定。

### 5.2 问题台账

- 每个问题一个永久编号（如 `P1-03`），改了严重程度也不换号。台账每轮随回信更新，驿窗保存每轮回信全文，并把上一轮台账带进下一轮送审；驿窗不理解内容，只保证记录不被悄悄改掉。编号稳定是便利，不是安全前提：每轮都要对账，漏掉的问题按未关闭处理。

| 状态 | 含义 | 解除阻断？ |
|---|---|---|
| 待修复 | 问题成立，还没修 | 否 |
| 待复核 | Claude 已返修并交了证据 | 否 |
| 已验证关闭 | ChatGPT 核实修复有效 | 是 |
| 判定不成立 | 有证据证明原判断误判或不适用 | 是 |
| 待决策 | 涉及设计取舍、风险接受、方案变更 | 否，走决策升级 |
| 范围外转单 | 确认和本次改动无关，已开 issue | 第 3 轮起的 P1 是；P0 任何时候都不是 |

- 谁能改状态：Claude 只能提议关闭、改级、转单，ChatGPT 确认后才生效；Claude 不能删问题。
- 范围内外由 ChatGPT 最后确认。第 3 轮起发现的范围外 P1 转单（开 issue）、不挡本单；范围内的 P1 即使是前几轮漏掉的，也照常挡。

### 5.3 每一轮的目的与四种出口

- **第 1 轮：建立基线**。定受审范围和受审版本，列出阻断问题、非阻断建议和验证要求。
- **第 2 轮起：围绕没关闭的问题**。范围是原问题、返修 diff 及其直接影响的路径，以及原审查前提是否因改动失效。Claude 写本轮目的，ChatGPT 判断够不够、必要时调整范围。双方都能要求「这轮重新全面审」，但要说明实质变化（接口、设计、安全边界）。不预设每一轮做什么，问题都关闭了就提前结束。

| 审查出口 | 条件 | 驿窗怎么做 |
|---|---|---|
| 通过 | 本次范围内没有仍阻断的 P0/P1；历史阻断问题都有最终处置；返修没带出新的阻断问题；P2/P3 都有处理结果；审过的就是当前版本 | 结束，**通知常浩**（不用他确认） |
| 返修 | 还有阻断问题，**而且下一轮有明确的、和上一轮不同的、能改变判断的工作**（有可行的修法、有新的验证价值）。同一问题上次修失败，说清为什么失败、换了修法，可以再来一轮；同样的思路再补一次不行 | 未到上限：转回 Claude 返修；到上限：见 5.5 |
| 证据不足暂停 | 有问题但缺关键验证材料 | 转回 Claude 并停自动往返；补齐后再送就续上。**这一轮照样计数** |
| 决策升级 | 要改已批准的需求、验收标准或关键安全假设；要接受风险；或已没有可信的修法 | 转回 Claude 并交常浩。只调整内部函数或测试方案、不碰这些边界的，不升级 |

下一轮没有新价值、又不满足通过时，ChatGPT 应选证据不足暂停或决策升级，不选返修。

### 5.4 计轮与两种计数

- **计一轮**：ChatGPT 做了一次实质审核（回信给出四档出口之一），包括证据不足暂停。
- **不计轮**：送审前材料不齐被驿窗拦下；传输失败；只请 ChatGPT 补格式。
- **授权周期轮数**：从第一次送审或常浩最近一次介入（插话、授权续审）起算，常浩介入后从 1 重计。上限按它判断。
- **审查链总轮数**：按任务（同一验收目标）认，**永不重置**：换 head SHA、换会话、换 PR、拆单、换工单编号都接着算；台账同样永不清空。续审要关联原单。总轮数用于展示、运行记录和价值评估。

### 5.5 上限与机械控制（驿窗执行）

- **上限**：本次授权周期最多 5 轮，取驿窗设置「接力审核上限」（默认 5，工程审查与思维评审共用）。
- **第 4 轮预警**：第 4 轮回信后仍要返修，转回时提示「下一轮是最后一轮」。
- **到顶**：第 5 轮回信不是「通过」，驿窗停下，发专门的到顶提示，卡上列五轮回顾（每轮出口、新增与关闭的问题），请常浩介入确认去向（第 8 节）。第 5 轮通过就照常结束并通知常浩。
- **通过通知**：任何一轮通过（没到上限也一样）都通知常浩。
- **版本锚点、格式补一次**：见第 4 节。
- 常浩授权继续时，`extra` 写明谁授权、为什么、目标，并记进第 7 节运行记录。

### 5.6 不变的部分

- 审查通过不等于合并、部署或上线授权。
- L0 不送审。

**落地边界**：这是统一解释，各项目规则各自开单同步，并与驿窗第 2 批同一天合并：

## 8. 人工必须决定的事项

- 合并授权（常浩说「合并」，或按各项目已批准的自动合并规则）。
- 到顶后的去向：收缩范围、重新设计、补证据、换审查手段，或授权新一个授权周期（`extra` 写明理由和目标）。
- 决策升级：改需求、验收标准或关键安全假设，风险接受。
- L3 的动作授权与风险接受。

## 9. 价值评估

- 关键发现：经核实、作者原本没发现的 P0/P1。P2/P3 和措辞建议不算关键发现。
- 每次运行记：风险级、审查链总轮数、P0/P1 数、是否到顶、是否拆单、常浩介入次数、从第一次送审到收口的时长。
- v0.3 上线后观察一批真实交付（剔除测试单和已修好的系统故障），和 v0.2 比：交还常浩的比例有没有下降；每单轮数和耗时分布，有没有拿一堆没价值的轮次换少量省心；通过后问题重开的次数；到顶次数与原因；台账缺失、版本对不上、异常重置的次数。不预设「多数在几轮内通过」。
- 反向信号：通过后问题重开变多；到顶比例明显高于 v0.2 的超预算比例；拆单重置轮数再次出现；L0 改动被送审。
- 最要先验证的前提：ChatGPT 能不能跨 5 轮可靠对账。上线前用故意改号、漏项、误关闭的模拟台账测一次；不稳就加强记录保存和对账，不加更复杂的停机规则。
