# MA-01 思维评审接力｜模式契约 v0.1

- 状态：运行中（主 Skill 已发布）
- 主 Skill：my-skills `skills/thinking-review` **1.0.0**（合并提交 `2839e91`，my-skills#66）。下文写「Skill 第 N 节」都指这个版本的 `SKILL.md`。
- 契约来源：从 thinking-review 1.0.0 与两次真实接力反推（I-MA-1，#1）；边界见《项目体系重构 V1.3》第 3 节；修订依据见 [docs/design/2026-11-07-V1.0修订表.md](../docs/design/2026-11-07-V1.0修订表.md)。

本契约只写 Skill 没有的内容（模式身份、和别的模式的分界、接口、状态语义、证据、价值评估）。触发、准入、退出的细则以 Skill 为唯一真源，这里只引用，不复述。

## 1. 目标

在方向性问题上引入一个不共享原推理链的思考者（ChatGPT High），在大量投入实施前校准问题定义、关键前提和路线选择；想清楚就退出，交回执行。要消除的单 Agent 风险：原作者自己的假设没人质疑，错了就是大返工。

## 2. 适用 / 禁用

- 适用：当前要解决的是「方向对不对」（Skill 第 2 节的 A 类），且过了准入（Skill 第 3 节）。
- 禁用：
  - 实现对不对 → 转 [MA-02](MA-02-engineering-review.md)；
  - 目标和路径都清楚 → 单 Agent 直接做（M0）；
  - 已有有效结论、又没有新证据 → 继承结论，不重送（Skill 第 3、8 节）。
- 与 MA-02 的分界：看「当前这一刻要解决的问题」，不看项目类型或有没有代码。A+B 混合时拆开，依赖 A 结论的 B 等 A 收口后再做（Skill 第 2 节）。

## 3. 角色

| 协作角色 | 默认承担 | 说明 |
|---|---|---|
| Owner | 常浩 | 定目标、拍板重大取舍、授权；可以随时发起、否决或覆盖 Claude 的判断 |
| Thinker | Claude（或最初形成方案的一方：常浩与 ChatGPT、其他 Agent） | 方案先在常浩和 ChatGPT 之间形成时，Claude 接手后先独立分析，只送增量（Skill 第 4 节） |
| Challenger | ChatGPT High（聊天模式） | 独立质疑；只看得到送审包，看不到原对话，也看不到本机文件 |
| Coordinator | Claude | 判断是否发起、处理回信、维护决策记录 |

Hermes 默认不参与。只有当这个问题本身属于 Hermes 委派的长期任务时，才由 Hermes 记录结果（见 V1.0 第 6 节）。

## 4. 输入与交接物（接口）

- 发起：调用驿窗 `relay_to_chatgpt`，标题以「思维评审｜」开头，按「思维评审｜<项目>｜<待决问题短名>」写。送审包的结构和评审指令照 Skill `references/relay.md` 第 2、3 节。
- 回信接口：回信最后两行固定为「评审出口：…」「结论：…」。驿窗只认这两行，正文里其他「结论：」不算。
- 留档：每个待决问题一份决策记录，模板为 Skill `references/decision-record.md`，放在所属项目约定的设计文档目录。
- 运行依赖：要有装了 postpane#209 的驿窗。已核实：装机版本 `f1b8bdb870a8`，实机往返通过（见第 7 节）。驿窗不可用时可以人工转交，但要在决策记录里写明实际怎么传的。

## 5. 状态语义与停止条件

| 评审出口 | 驿窗协议词 | 含义 | 之后 |
|---|---|---|---|
| 成熟退出 | 通过 | 核心判断已有依据 | Claude 按已定路径执行，不再送审 |
| 转其他路径 | 通过 | 剩下的是工程实现或普通执行 | 转 MA-02 或 M0 |
| 继续深化 | 需修改 | 还有标为「需深化」的项 | 只针对这些项进入下一阶段 |
| 证据不足暂停 | 需修改 | 再讨论也不会有新信息 | 先取证；拿到证据前不送审、不实施 |
| 决策升级 | 交常浩裁决 | 剩下的是偏好、资源、授权或风险接受 | 交常浩拍板 |

成熟条件、各出口的细则和重新进入的条件，见 Skill 第 7 节、`references/exit.md`。

## 6. 轮次与超时

- 阶段（全景 → 深化 → 收敛）是思考方式，不是固定轮数。一次回信可以直接收口（Skill 第 5 节，`references/stages.md`）。
- 驿窗的自动往返和工程审查共用同一个上限：本次授权周期最多 N 轮（驿窗设置「审核轮数上限」，默认 5、可调 1–9），到上限那一轮仍是继续深化或证据不足暂停就停下交回常浩，任何一轮评审收口都通知常浩（通知界面在驿窗第 3 批）；常浩介入后授权周期从 1 重计。到顶后再送同样拒收；常浩授权继续时填 `extra`，口径和工程审查一样（这一轮须由外面的话开头）；同一会话或工作目录里有到顶还没了结的思维评审时，新开思维评审同样须由外部消息开头（但不用填 `extra`），闲置自动结束的不算了结（MA-02 第 5.5 节「到顶后续审与新开」）。这是工具层的安全上限，不是认知结论。只共用上限与机械控制（计数、格式补一次、通过通知），不套用 MA-02 的问题台账和 P0/P1（[MA-02](MA-02-engineering-review.md) 第 5.5 节，`references/relay.md` 第 4 节）。
- 内容没有实质变化不重送；缺事实先取证，不靠多轮讨论来模拟事实。

## 8. 人工必须决定的事项

- 目标、范围、授权，以及 GPT 论证代替不了的偏好与风险接受（评审出口为「决策升级」时）。
- Claude 在授权范围外顺手做出的方向性改动，先交常浩决定撤回还是保留，再谈评审（Skill 第 3 节）。
- 评审收口不等于上线或合并授权。

## 9. 价值评估

- 衡量口径：这次评审有没有实质改变决策、关键假设或执行边界。不套用工程缺陷等级（P0–P3），也不看意见条数。
- 每次运行记：接力 id、轮次、评审出口、实质改变（有/无，写一句是什么）、被驳回的意见数、常浩介入次数。日志只能证明「用过」，价值要看这一列。
- 反向信号（出现就复盘 Skill）：同一问题重复送审；评审出口格式错误，被驿窗拦下交给常浩；B 类问题误进 MA-01（参考 thinking-review `research/cases.md` C-11～C-14）。
