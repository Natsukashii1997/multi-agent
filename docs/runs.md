# 运行记录：runs/runs.jsonl

所有协同模式共用这一份运行记录，每次运行一行 JSON。目的是回答「这次协同比单 Agent 多带来了什么」：驿窗 `handoffs.json` 和 agent-kit `skill-usage.jsonl` 只能证明用过（修订表第 7 节）。这也是 agent-kit《工程流程》第 8 节第 1 条要求的「证据随机制出生」：本仓库的模式在这里记。

`tests/runs-format.test.mjs` 会逐行检查字段。

## 什么时候记

- 用了一次协同模式，就记一条：MA-01、MA-02 的真实接力；按 [candidates.md](candidates.md) 组织的 MA-03、MA-04、MA-06 试跑。
- 驿窗自身的功能实测也可以记，`kind` 写 `实测`；判断过、决定不走这个模式的，`kind` 写 `未协同`。统计协同运行次数和价值时，这两类都排除。
- 一次运行跨了几个接力（续审、无头会话代发），记成一条，`handoffs` 列出全部接力 id。
- 运行结束后由发起方记录，和交接放在同一个提交里。契约第 7 节的表格是给人看的摘要，有争议时以本文件和驿窗 `handoffs.json` 为准。

## 字段

| 字段 | 类型 | 说明 |
|---|---|---|
| `run_id` | 字符串 | `R-YYYYMMDD-NN`：日期取 `started` 的北京时间日期（没有 `started` 的取记录当天），序号看文件里这个日期已有的最大号加一，全文件唯一 |
| `case_id` | 字符串或 null | 同一个任务走了几个模式（例如 MA-03 验证后再走 MA-02 审查）时，几条记录写同一个 `C-<短名>`；只走一个模式的写 null |
| `mode` | 字符串 | `MA-01`～`MA-06` |
| `kind` | 字符串 | `真实`（真实使用）、`实测`（测试接力链路本身）、`未协同`（判断过、决定不走这个模式，作负向评测样本） |
| `title` | 字符串 | 给人看的名字 |
| `handoffs` | 数组 | 驿窗接力 id（`h` 加 13 位十六进制）；没走驿窗的写 `[]` |
| `pr` | 字符串或 null | `owner/repo#号` |
| `risk` | 字符串或 null | `L0`～`L3`；思维评审、新规则以前没定级的写 null |
| `rounds` | 整数 | 审查或评审回信的次数；没送审写 0 |
| `exit` | 字符串 | **最后一次回信**的出口：MA-01 用契约第 5 节的出口；MA-02 用 `通过 / 返修 / 证据不足暂停 / 决策升级`；没送审写 `未送审`；候选模式按候选卡写一个短词 |
| `resolution` | 字符串或 null | **任务最后怎么收口**，和 `exit` 分开记：`已合并`、`补改未复审后合并`、`未合并`、`进行中`、`不适用`（思维评审等不产出 PR 的） |
| `reported_p0p1` | 整数或 null | 回信里报出的 P0、P1 总数 |
| `verified_findings` | 整数或 null | **经核实的增量发现**：MA-02 是作者原本没发现的 P0/P1（契约第 9 节「关键发现」）；MA-03 是验证方发现、经作者复现确认、作者自测没发现的缺陷数。没核实写 null |
| `changed_decision` | 布尔或 null | 是否实质改变了决策、假设或执行边界（MA-01、MA-04 的价值口径） |
| `baseline` | 字符串或 null | 单 Agent 原来做到哪一步：作者自测结果，或 MA-04 对照组报告的位置。没记录写 null |
| `over_budget` | 布尔 | 是否超出 MA-02 审查预算 |
| `split` | 布尔 | 是否把同一验收目标另开新单、重置了轮数 |
| `owner_interventions` | 整数或 null | 常浩介入的次数：拍板（超预算后的去向、风险接受、决定跳过送审）、授权续审、手动续审、流程外要求送审。按流程本来就该做的送审、说「合并」不算 |
| `started` / `ended` | 字符串或 null | 北京时间 `YYYY-MM-DD HH:mm`，取第一次送审和最后一条回信 |
| `evidence` | 字符串 | 去哪里核对：契约章节、PR、提交号、证据目录 |
| `note` | 字符串 | 一两句收口情况；没核实的写「未核实」 |

null 表示没核实或不适用，不要用 0 代替。`reported_p0p1` 和 `verified_findings` 分开记：回信报了几条，不等于其中几条是真的、作者原本不知道的。

## 怎么用

- 看价值：收益看 `verified_findings`、`changed_decision`，对照 `baseline`；成本看 `rounds`、`owner_interventions`、起止时长。只统计 `kind` 为 `真实` 的记录。
- 看审查意见有没有落实：比 `exit` 和 `resolution`，例如出口是「返修」、收口是「补改未复审后合并」。
- 看规则有没有守住：`split` 为 true 或 `over_budget` 为 true 的记录，回去看当时有没有授权。
- 记满 10 条真实运行后，再考虑写汇总脚本；现在直接读文件就行。
