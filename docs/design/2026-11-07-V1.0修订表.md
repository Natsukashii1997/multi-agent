## 2. 第 1～2 节｜角色
- 协作角色统一为六种：Owner（常浩，目标、取舍、授权、最终裁决）、Thinker（Claude / ChatGPT / 常浩）、Builder（Claude Code）、Challenger（ChatGPT High）、Verifier（Claude 自测；Codex 可作为独立验证方）、Coordinator（Claude；长期委派可由 Hermes 承担）。角色是职能，不要求每次都出现。
- Agent 档案分两类：静态档案写擅长领域；动态档案写额度与成本、能读到的上下文、实际执行能力、响应成本、值守或授权要求。另加一条选择约束：相对方案作者的独立性（自测有价值，但不算独立验证）。没核实的动态条件，不能写成模式的必备能力。
- **Hermes 只有一个，即常浩的数字分身。删掉 Hermes Enterprise 行，正文不再区分个人/企业**（常浩 11-07 原话）。
- ChatGPT High：默认依据送审包和可获得的 PR 证据判断；能否读仓库、跑命令，取决于当次连接的工具和授权，不写死。
- Codex：历史上做过独立复核（数码世界 9–10 月）；10-31 起额度不足，审查改走 ChatGPT。不再写成当前默认的验证方。
- Hermes 不因底层用某个模型，就自动继承该模型 CLI 的能力或额度。

模式 × 角色（候选默认，不是强制配置）：

| 模式 | 核心参与者 | 分工 |
|---|---|---|
| MA-01 | 问题发起者 + ChatGPT High + Claude（按需） | 原始思考、增量质疑、方案修订 |

| MA-06 | Claude + 独立诊断方（候选） | 根因分析、反证、诊断收敛 |

## 3. MA-02 模式卡｜分级、轮数、退出
- 起点是送审前的风险判断与证据要求，不是收到 PR 后才选审查方式。
- 默认 Claude 执行并自测，ChatGPT High 经驿窗做独立工程审查。
- **审查预算（常浩已拍板）**：

  | 级别 | 自动审查预算 | 额外要求 |
  |---|---|---|
  | L0 | 0 轮 | 机械检查 |
  | L1 | 默认 1 轮 | 自测和增量证据 |
  | L2 | 最多 2 轮 | 自测、回归与独立主审 |
  | L3 | 最多 2 轮 | 前置风险分析、必要的独立验证、常浩授权 |

  （否掉 Claude 草案里 L2 3 轮、L3 4 轮：风险越高应前置更严，而不是循环更多。）
- 轮数从第一次正式送审起算；换 head SHA、换工单编号都不重置（SBX-8 拆成新单的情况就是绕过）。常浩授权的专项续审要写明目标、次数和理由，并关联原单。
- 超预算、重复修复失败、关键证据不足、出现需要改原方案的问题：停止自动往返，转重新设计、补证据或常浩裁决。
- 审查语义分四档（通过、返修、证据不足暂停、决策升级），驿窗传输仍是「通过/需修改」二态。协议扩展前，「暂停」「升级」要在正文写明禁止自动返修。
- 可以调用独立验证作为证据，但不默认绑定 Codex。
- 这是统一解释，不直接改写其他项目已生效的规则：agent-kit「两轮不过停」= 默认升级节点；DT-ORC 6.4「两轮」= 自动循环预算；驿窗「两轮」= 传输默认预算。实际改动由各项目单独开单。

## 4. MA-03 模式卡｜候选
- 不宣称持续运行。启动前核实：验证方可用、能访问目标环境、能独立执行并留下可复验证据。
- 至少两次真实试跑后，再看它有没有独立触发条件、独立交付物和稳定收益，才决定要不要从 MA-02 的验证环节晋升为独立主 Skill。
- Codex 暂时不可用，不等于独立验证没有价值。
- 2026-11-08 补：候选卡（试跑怎么做、能判对错的晋升条件、验证方不绑定 Codex）见 [../candidates.md](../candidates.md)，MA-04～MA-06 也在那里。

## 5. 第 6.4 节｜边界
multi-agent 只持有可复用的模式契约、角色协议、跨模式接口语义和评测定义。Hermes 控制面、Hermes→Multica 适配代码、Multica 运行流程归 digital-twin。共享适配器要等出现两类独立消费方、并明确共用需求与维护责任后，才考虑升格。不建 `adapters/` 目录。

## 6. 第 7 节｜Skill 与契约
- **主 Skill 映射（常浩已拍板）**：每个启用的场景有一个明确的主 Skill 入口；多个场景可以共用同一个模式 Skill，不强制一个场景新建一份。
- multi-agent 契约写：模式身份、适用边界、角色关系、接口要求、最小证据、状态语义、价值评估。my-skills 写：操作步骤、触发细则、轮数处理、退出流程。具体规则在契约里用版本化引用，但契约要保留其他消费方（如 Hermes）读得懂的最小接口定义。
- 契约准入和 Skill 发布准入是两回事：新 Skill 照走 my-skills 七站两闸，不因为有契约就自动通过。
- 前置路由入口：各模式 Skill 写自己的边界（「不归我管，转 MA-xx」），另在运行时一定会读到的位置（全局 CLAUDE.md / Codex AGENTS.md 指向的规则）放一个最小路由入口。只写在 agent-kit 文档里不会被自动读到。

## 7. 第 8 节｜运行记录与评测
- 先复用驿窗 `handoffs.json`、agent-kit `skill-usage.jsonl` 和现有复盘机制，不建观测平台。
- 单次驿窗接力用 handoff id 当运行标识；跨多次接力、多 Agent、跨工具的协同运行，另给关联标识。标题前缀只给人看，模式 ID 要在证据记录里明确映射。
- 日志只能证明「用了」，不能证明「有价值」。指标至少分开记：运行次数、被采纳的有效发现、返工轮数、额外协调成本。工程类以 P0/P1 计关键缺陷；思维评审以「是否实质改变了决策、假设或执行边界」计，不套工程缺陷等级。
