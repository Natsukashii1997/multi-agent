# 多 Agent 协同体系｜角色、场景、模式与进化架构 V1.0

> 日期：2026-11-07  
> 性质：项目级架构方案与候选模式清单；不是既有系统全部验证通过的证明  
> 范围：个人多 Agent 协同能力项目 `multi-agent`，覆盖角色与场景、协同契约、主 Skill、Multica/驿窗适配、Hermes 接入边界及效果验证。企业数字分身另有隔离约束。  
> 原则：**默认单 Agent，增量收益有证据才升级协同；同一事实单一权威源；复用已有系统，不为协同而协同。**

## 0. 核心结论

1. 不按照“多少个 Agent”或“谁先调用谁”来数模式。候选需求先分为 16 个有代表性的场景；多数场景是少数基础模式的不同参数与角色组合，不能变成 16 套独立系统。
2. 保留既有模式编号 MA-01～MA-05，另设 MA-06 根因诊断会诊作为待验证候选。五种基础模式包括：思维评审、工程审查、独立验证、并行研究综合、自治委派。模式 06 并不默认立项。
3. 多 Agent 项目负责**模式契约/角色能力注册/协同适配规范/模式效果证据**；`my-skills` 负责正式主 Skill 与七站两闸；`Multica` 是编排执行手段而非 Agent；`postpane` 是可交互的传信与回执产品；Hermes 是长期任务目标与结果的责任代理，不是任何模式必经的一跳。
4. 优先从已有 `thinking-review`、Claude/Codex 工程测试、驿窗接力和 DT-ORC V4.0 Multica 有人值守工程中反向归纳契约，绝不同时从零建设六份工作流。
5. 只在长期委派、跨会话状态、主动发现任务、依授权派单、持续追踪与汇报等有明显价值时引入 Hermes。个人与企业 Hermes 的记忆、权限、凭据和执行路径严格隔离；企业域不得因为本架构设计而接入个人 Multica/私人 Vault。
6. 同一模式的核心 Skill 需要经历实际运行→效果/失败反馈→归因→提出增量→回归评测→新版本发布，但不能依据单次负反馈自动修改正式 Skill。

## 1. 六个概念必须分开

| 概念 | 回答什么问题 | 例子 | 真源建议 |
|---|---|---|---|
| 场景 Scenario | 为什么需要协同，最终要完成什么 | 架构决策、PR 风险复核、跨数据源核算 | 多 Agent 场景目录 |
| 模式 Mode | 多角色怎样协作、交接、收口 | MA-01 独立思维评审 | `multi-agent` 的模式契约 |
| 角色 Role | 在本次协作中负责什么，接受何种检查 | 生产者、独立质疑者、验证者、总协调者 | 多 Agent 角色能力注册 |
| Agent 实例 | 谁在这次任务里扮演角色 | Claude Code、Codex、ChatGPT High、Hermes | 运行时绑定并记录身份和能力 |
| 主 Skill | 怎样正确启动、运行、判定与总结一个稳定模式 | `thinking-review` | `my-skills` 正式版本 |
| 执行与传输 | 如何真正运行、派单、交接、反馈和审计 | Multica、驿窗、GitHub PR | 各产品自身仓库与日志 |

明确区分：**协同模式不是 Skill，Skill 也不是执行引擎。**“一个场景一个主 Skill”的合理落法是：每个已经稳定且获准正式化的模式设置一个主 Skill；同模式下的细分业务场景使用配置和场景画像，不因为多了一个案例就复制一份 Skill。未稳定场景先保留为候选，不提前铺开。

### 三种常见执行拓扑（和“协同目的”正交）
- 串行接力：A → B → A，可用于思维与审核。
- 独立并行：A 与 B 在隔离上下文内各自做研究/方案/验证，再对比并综合。
- 总控委派：目标责任主体 → 多个受约束的执行/验证角色 → 证据汇总 → 结果验收；适合 Hermes 的长任务。

同一目的可能使用不同拓扑；同一拓扑也可能服务不同目的。没有必要为“2 人串行”“3 人串行”“4 人并行”分别建立新项目。

## 2. Agent 角色与能力矩阵

### 2.1 核心角色

| 对象 | 建议定位 | 最适合的任务 | 不应默认承担 | 状态说明 |
|---|---|---|---|---|
| **用户** | 目标所有者、重大取舍/授权最终裁决者 | 定目的、优先级、接受风险、对外交付/重大合并授权 | 每一步都亲自分配和复述上下文 | 始终保留最终授权权利 |
| **Hermes Personal** | 长期目标/项目状态责任代理；跨会话计划和结果收口 | 项目总览、主动发现、授权记录、派单、审计、跟踪、三报、记忆引用 | 默认当每次代码审查员或替代 Claude/Codex 的技术判断 | 主线；自主接 Multica 的端到端链路需按实际验收判断，不能以有人值守首跑充当自治证明 |
| **Hermes Enterprise** | 独立企业任务域的长期助理 | 企业知识、团队任务、带教、已授权的企业业务流程 | 接触私人 Vault、个人 Multica/ORCA、个人记忆与凭据 | D19 双域隔离为既定约束；不得未经单独授权接个人执行链 |
| **Claude Code** | 带项目上下文的主分析/设计/工程实施角色 | 复杂问题拆解、方案深化、代码建设、修复、交接与必要时发起思维评审 | 自动成为其自身产出的唯一独立验收者 | 依据具体任务可担任主思考者、开发者或整合者 |
| **ChatGPT High（聊天模式）** | 独立认知质疑与高强度审查 | 问题定义与路线选择、方案批判、工程改动逻辑审查、关键分歧收口 | 假装拥有未提供的本地运行日志或执行过真实测试；替代最终授权 | 已存在经驿窗接力的 thinking-review 实践 |
| **Codex** | 独立工程验证/结构化建造与分析角色 | 异构工程实现、可执行测试、复现、回归、证据检查、结构化沉淀与核算 | 仅因模型不同就自动认为“独立”；与被审对象共享未经披露的预设结论 | 历史上偏结构化沉淀，现有工程实践中承担独立测试/验收；按场景指定角色 |

### 2.2 非默认现役、历史或可选角色

- **Aily**：此前定位为飞书秘书/事实记录角色。可在真实会议、沟通、日程输入场景提供原始事实；目前不能假定已部署或纳入每条协同链。
- **OpenClaw / 外部独立顾问**：早期定位是不了解个人既有推理链路的外部视角。现有数字分身 PRD 记录旧 OpenClaw 系统清理，**不建议直接列为当前活跃执行 Agent**；如确有认知独立性需求，先抽象为“外部盲审角色”，验证当前可用实现后再绑定工具。
- **专用子 Agent / 搜索/数据专家**：仅在能独立完成可验收子任务、具备实际工具权限且不会增加大量同步成本时启用。

### 2.3 非 Agent 的重要系统

- **Multica**：执行引擎/任务与角色编排工具；不是另一个负责判断目标的“人格”。通用集成规范归多 Agent 项目；现有 DT-ORC V4.0 的具体任务、授权适配与业务状态仍由数字分身项目维护。避免为了统一而迁移成熟的私有工作流。
- **驿窗 PostPane**：人机界面、Claude↔ChatGPT 传信、回执、状态和会话绑定；不拥有模式判定规则的唯一真源。
- **GitHub / 仓库**：工程事实、PR、提交 SHA、CI、issue 的权威出处之一；提交和测试证据不能被 Agent 的“已完成”口头陈述替代。
- **`my-skills`**：正式可执行方法的唯一版本真源；模式契约引用 Skill，不复制整篇文本。
- **`agent-kit`**：横向工程安全与规范；任何协同模式不得绕过其权限、审查及证据规则。
- **Obsidian 知识库 / Vault**：工程仓库和知识正文真源分离；按信息敏感等级与目标域权限使用。

### 2.4 角色选择约束

1. **初始思考者不固定**：用户可能先与 ChatGPT 形成方案，再交 Claude；也可能从 Claude、Codex 或 Hermes 开始。接手者应独立判断后只送新增异议，不能把同一 GPT 方案原封不动交回 GPT 做“独立确认”。
2. **生产者与验证者需要操作独立性**：至少有独立的证据读取/测试过程、清晰的职责与版本绑定；两个不同模型只是辅助条件。
3. **专业判断与运营判断分开**：Hermes 可以检查证据是否齐全、权限是否符合、任务是否闭环，但不能以自己的一句“通过”代替独立技术评测。
4. **模型/产品能力与角色不完全绑定**：Claude 可以做研究，Codex 可以开发，ChatGPT 可以先形成战略框架；默认分工是优化起点，不是角色禁令。
5. **权限从不因角色名称自动增长**：审查员不是合并者，执行者不是审批者；“未收到明确授权”不能通过模式切换规避。

## 3. 候选场景全景：16 类需求，不等于 16 套协同模式

标注：高 = 有明确的额外协同价值条件；条件 = 只在高风险/高不确定时启用；低 = 默认单 Agent。这里的级别是**建议**而不是实证收益。

| # | 真实使用场景 | 常见单 Agent 缺口 | 推荐方式 | 增量价值等级 |
|---:|---|---|---|---|
| 01 | 重大产品与架构路线决策 | 核心前提未被独立质疑，错了大返工 | MA-01：Claude/ChatGPT 思维评审 | 高 |
| 02 | 复杂业务策略、定价、资源取舍 | 单一视角过度依赖既有假设 | MA-01，必要时 MA-04 取独立证据 | 条件/高 |
| 03 | 需求澄清、PRD、任务拆分 | 误解目标会放大到大量下游工作 | 默认 Claude；重大前提再 MA-01 | 条件 |
| 04 | 竞争性方案/架构备选路线 | 只有一条路线、过早收敛 | MA-04：并行独立方案，最后比较 | 高（确有真实取舍时） |
| 05 | 复杂研究、竞品、技术选型 | 单渠道遗漏、来源相互矛盾 | MA-04：独立检索，综合查证 | 高（重要信息依赖外部证据时） |
| 06 | 新产品设计中的用户体验探索 | 设计方案差异大而无比较依据 | 单 Agent 先出方案；必要时 MA-04 | 条件 |
| 07 | 中高风险 PR 审查 | 作者盲区、边界处理遗漏 | MA-02：作者 + 独立审查者 | 高 |
| 08 | 功能完成后的独立测试/回归 | 作者自测容易同源偏误 | MA-03：Claude ↔ Codex，证据与复现 | 高 |
| 09 | 权限、迁移、原子写入、长期服务 | 失败成本高，普通审查不足 | MA-02 + MA-03，依据风险分阶段使用 | 高 |
| 10 | UI/交互、截图和可用性验收 | 视觉理解与实现证据不一致 | 默认 UI 体系截图自检；争议时 MA-03/独立评审 | 条件 |
| 11 | 财务模型、业务指标、计算核验 | 公式同源错误、口径混淆 | MA-03 的数据验证画像，独立复算 | 条件/高 |
| 12 | 反复无法复现或无法定位的技术故障 | 单一路径反复修复却不接近根因 | MA-06 候选：独立假设与证据会诊 | 高（达到触发门槛） |
| 13 | 同一问题连续两次修复失败 | 代码故障或错误架构假设难分 | 先分类：MA-06 根因；重大前提变化 MA-01 | 条件 |
| 14 | 跨会话、长周期项目的自主推进 | 中断后状态丢失、工作无法持续 | MA-05：Hermes 总控 + 受限执行/验证 | 高（长期任务） |
| 15 | 定期项目巡检、异常提醒、例行三报 | 主要难题是持续性，非多种认知 | 单 Hermes 可完成就单执行；必要时委派用 MA-05 | 条件/低 |
| 16 | Skill/知识整理、经验萃取、日常文案 | 大多数是稳定的生产任务，不需交接 | 单 Agent + 现有 Skill；高风险成果才调用 MA-01/03 | 默认低 |

**注意区分模式和组合场景**：例如“完成一项高风险功能”可能按需先 MA-01 讨论架构，再 MA-03 测试，再 MA-02 对改动审查。它是一条基于证据串起的**任务路径**，不应该因此再建一个“工程流水线 MA-07 模式”。

## 4. 正式候选模式卡（MA-01～MA-06）

### MA-01｜思维评审接力（现有成熟基线）
- **目的**：对重大问题定义、根因、路线与决策前提进行独立认知校准。
- **触发**：重大架构/策略决策、已形成方案但关键前提未证、测试推翻基础假设、持续返工暴露方向性问题。
- **默认角色**：Claude Code（或其他任务主思考者）主推进；ChatGPT High 独立质疑；用户只对目标、资源、授权与剩余不可证分歧拍板。
- **实施**：经驿窗接力；“全景→关键深化→收敛”是思考阶段不是强制三轮；成熟退出、升级决策、证据不足暂停、转工程/直接执行四类出口。
- **主 Skill**：现有 `my-skills/skills/thinking-review` v1.0.0，继续使用，不重建。
- **不适用**：普通小修改、常规 PR 审查、纯执行、已充分论证又没有新证据的决定。
- **Hermes**：只有目标长期由 Hermes 委派、需要跨会话追踪或批准管理时参与；普通 Claude↔GPT 接力不加入。
- **关键价值**：早发现方向错误，减少重大返工，而不是审查轮数越多越好。

### MA-02｜工程审查闭环（优先固化）
- **目的**：独立评估实现是否满足任务要求、发现边界与逻辑风险。
- **触发**：中高风险 PR、跨模块改动、权限状态、数据迁移、执行器和自动化安全改动。
- **默认角色**：Claude Code 开发；ChatGPT High 经驿窗做独立工程逻辑审查，或 Codex 在有实际代码/运行权限的环境做工程复审；必要时原开发者返修。
- **交付**：绑定 `repo/base_sha/head_sha`、差异包、验收条款、可核实的测试材料、分级缺陷、明确通过/需修改/阻塞结论。
- **循环**：每轮对特定版本有效；下一轮只审核风险缺陷和关联回归；同一问题不无限返修，新缺陷不随意扩大范围。
- **主 Skill**：候选 `engineering-review`；已有 code-review 流程和接力经验优先复用；未正式准入前不声称已发布。
- **边界**：评审通过不等于 Merge 授权、部署授权或系统上线。

### MA-03｜独立验证与测试（优先固化）
- **目的**：让与实现者职责分离的角色使用独立证据对结果进行测试、复现与验收。
- **默认角色**：Claude Code 开发；Codex 独立测试与复核；必要时 Claude 修复并由 Codex 复验。
- **场景画像**：自动化脚本、权限/原子写入、前后端接口、UI 截图验收、数据计算模型、业务规则口径复算。
- **证据**：具体操作命令、版本 SHA、环境隔离、预期与实际、失败复现、测试覆盖与尚未证实的限制。
- **主 Skill**：候选 `independent-verification`。先从真实的 Claude/Codex 工程测试样本反推，避免重新造轮子。
- **边界**：测试通过不等于可发布；验证必须受限、不可因审查任务自动获得修改线上资源的权限。
- **Hermes**：长任务可以负责组织和收口，但不替 Codex 运行测试。

### MA-04｜并行研究与综合（待验证）
- **目的**：通过相互独立的信息搜集或竞争方案形成，比单路径更全面、可比较的证据和路线。
- **触发**：多条真实可行路线、证据来源差异大、信息缺口难由一个研究分支覆盖、后果明显的技术选型或策略决策。
- **角色**：Claude 或 ChatGPT 任主研究者；Codex/另一个独立研究 Agent 负责不同子问题或盲审；一个整合角色按证据权重和原始来源合并，避免多数投票。
- **实施方式**：先定义独立研究任务/对比维度和止点，再并行；成果不可通过互相摘录制造虚假的“多来源确认”。
- **主 Skill**：候选 `parallel-research-synthesis`，必须先有两次可复用、收益明确的真实运行再准入。
- **边界**：无高质量事实来源时，增加 Agent 只会增加猜测，应该先取证。

### MA-05｜自治任务委派与收口（架构明确、运行受控）
- **目的**：长期任务在明确授权与真实状态记录下跨会话推进，降低用户反复接管成本。
- **默认角色**：Hermes Personal 负责目标、优先级、派单、权限与状态、闭环汇报；Claude Code 负责开发/执行；Codex 负责独立验证；ChatGPT High 在需要时承担思维或工程审查。
- **运行**：Hermes 通过受限适配器驱动 Multica 的受支持任务；工程事实记录在 Multica/GitHub，目标状态记录在 Hermes；ChatGPT High 接力可通过驿窗，而不是假设它必定是 Multica 的 CLI Worker。
- **主 Skill**：候选 `autonomous-delegation` 只能描述通用准入、派单、核验与退出方法；Hermes 专属任务状态和审批实现仍留 digital-twin。
- **当前成熟度**：DT-ORC V4.0 Multica 的 M1 权限矩阵与 M2 有人值守首跑构成可复用证据；**Hermes 自主接入 Multica 的 M3/M4 仍需实证**。不能宣称无人值守自治完成。
- **边界**：高风险操作须按既有风险和授权门处理；未知结果先查 operation/run 状态，不盲重发；不得扩大 Personal Hermes 对 Enterprise 域的访问。
- **排除**：一次性 Claude↔GPT 思维评审不需要 Hermes 介入；单 Hermes 可完成的三报不强行升级为多 Agent。

### MA-06｜异常诊断与根因会诊（新增候选，不即刻正式化）
- **目的**：当单线修复反复失败或出现相互矛盾的症状时，使用两个独立诊断路径检验根因，避免继续盲目改代码。
- **触发**：同一缺陷多次修复失败、生产症状与测试结果矛盾、复杂跨组件竞态、持续运行故障无法定位。
- **角色**：Claude 负责复现与假设 A；Codex 负责独立假设 B/实验设计或反向测试；ChatGPT High 只在发现会推翻架构的方向问题时经 MA-01 参与。Hermes 仅在长周期故障任务或主动巡检派单时参与。
- **步骤**：隔离环境→固定共同事实→独立提出可证伪假设→设计区分实验→以真实结果淘汰假设→单责任修复→MA-03 复验。
- **主 Skill**：先作为候选记录、积累失败样本；若 MA-03+MA-01 已可充分覆盖，就不另建正式模式与 Skill。

## 5. 如何选模式：以“单 Agent”为默认基准

### 五个准入判据

1. **差异价值**：引入第二个角色可以提供原 Agent 所没有的独立判断、不同工具权限或不共享错误假设的验证吗？
2. **风险或返工成本**：遗漏错误会造成明显返工、误导决策、权限/数据风险吗？
3. **事实可验证性**：是否存在足够的来源、测试、数据或可复现实验，使协同结果可以比对？
4. **任务独立性与成本**：工作可合理拆分吗？交接和上下文恢复成本会不会高于实际节约？
5. **历史有效性**：同类真实任务里，第二个 Agent 是否曾找到第一位没有发现的关键问题？如果没有，是否只需做一次小规模试验？

### 路由决策

```
开始
  ├─ 目标清晰、低风险、可单人完成 → M0 单 Agent 直接执行
  ├─ 方向/重大前提存在高代价不确定性 → MA-01
  ├─ 正在审代码/实现边界与风险 → MA-02
  ├─ 需要独立测试、复算、实证复现 → MA-03
  ├─ 需要多个不同研究视角/备选方案 → MA-04
  ├─ 长期跨任务推进且有授权与状态管理 → MA-05（Hermes）
  └─ 已持续修复失败，需对根因做可证伪实验 → 候选 MA-06
```

**优先做证据，而非增加审查**：如果争议是一个没有任何人拿到数据的事实问题，正确动作是取证；不应召集 Claude、GPT、Codex 连续讨论尚不存在的数据。

### 升级、降级、停止
- M0→M1：单角色产出已足够，但高风险/高不确定/独立性缺口明确；先只加一个角色。
- 两角色→三角色：仅当第三方拥有明确不可替代职责，如真实可执行测试或新的独立信息源。
- 多角色→单角色：后续交付已常规化、风险降低、反复审查没有增量信息或总体耗时明显增加。
- 任何模式：达到明确退出条件即结束，不以“还可以多审一轮”为理由继续。
- 个人分身参与应为 opt-in 情境规则（长期计划/授权/状态），不是所有模式的全局前置条件。

## 6. Hermes 与多 Agent 协同：职责与边界

### 6.1 Hermes 有价值的参与条件

- 任务**跨会话或跨天**，必须保留目标、依赖、待办、限制与结果。
- 需要**主动触发或状态巡检**，而非用户当前已直接发起短会话。
- 任务涉及**跨项目协调或长期资源排序**，但仍受用户确定的目标与优先级约束。
- 需要**授权申请/回执/异常升级/最终汇报**的统一责任方。
- 一个任务下有多个子任务和多位执行者，需要持续知道“谁负责下一步”以及“目前证据是否完整”。

### 6.2 Hermes 不该参与的情况

- Claude 和 ChatGPT High 一次思维评审；只是为了转信无须让 Hermes 再复述一层。
- Claude Code 自己可以运行的简单功能开发。
- 不涉及长期状态的一次性 Codex 测试、快速复算。
- 只是日常信息记录、个人摘要或模板化文案的单 Agent 工作。
- 企业数字分身试图直接复用个人域的 Multica/私人数据链路。

### 6.3 两条实际链路的对照

**链路 A：直接协同（无 Hermes）**  
用户或 Claude 发现重大方案不确定 → Claude 按 thinking-review 判断准入 → 驿窗把增量问题发给 ChatGPT High → ChatGPT 给出独立评审及成熟退出/暂停/升级 → Claude 判断采纳并继续执行。  
所有正式 Skill 源自 `my-skills`；驿窗只管真实传信和回执。

**链路 B：长期自治委派（Hermes 有价值）**  
用户明确目标和授权边界 → Hermes 拆任务并记录目标状态 → 在已有权限下选 MA-02/03 或其他模式 → Multica 组织实际受限 Worker（Claude/Codex 等） → 按需经驿窗送 ChatGPT High → Github/Multica 形成执行证据 → Hermes 核查任务状态和授权、向用户汇报/升级 → 依据明确验收关口关闭任务。  
**目前不能将“这条架构链路已设计”写成“无人值守已实测通过”。**

### 6.4 Multica 归属争议的解决办法

- `multi-agent`：拥有通用协作模式、可复用的 Multica 适配约束/角色绑定接口规范、运行证据格式与跨场景验证方法。
- `digital-twin`：拥有 DT-ORC 的 Hermes 专属 `twin_state`、授权适配、专用任务泳道、任务状态、运维与业务规则。
- Multica 自身安装/源码是执行依赖，不要因为“属于多 Agent 能力体系”就强行把现有工作树挪入新仓库。
- `postpane`：负责 Claude↔ChatGPT High 的用户可见接力；没有必要伪装成 Multica 的内建模型 Worker。
- 允许 digital-twin 先保留已有运行实现；当确证多个非 Hermes 场景能复用同一块无私有状态的适配器时，再进行抽取。**先归属清楚，再按证据决定是否迁代码。**

## 7. 模式契约、主 Skill 与运行证据

### 7.1 所有模式共用的八个核心字段

1. **目标**：模式要消除什么单 Agent 风险、产生什么增量。
2. **适用/禁用条件**：何时值得启动，何时必须直接执行或等待证据。
3. **角色及责任**：谁是生产者、独立挑战者、验证者、总控与最终裁决者；实际 Agent 在运行时绑定。
4. **输入与交接物**：具体问题、必要上下文、不可缺少的版本/数据与预期输出。
5. **停止条件**：成功/证据暂停/转交/升级/无收益停止，不要求必须走满轮数。
6. **往返与资源上限**：默认一轮判断、何时允许第二轮、无新证据不重复发；高风险限制可覆盖默认。
7. **证据真源**：每项结论回到具体 PR、SHA、测试输出、研究来源或决策记录。
8. **用户授权点**：重大取舍/部署/删改/风险接受何时必须明确用户审批。

按运行风险扩展：仓库及 worktree/会话 ID、head SHA、runner 及授权身份、操作幂等键、超时/断点恢复、外发脱敏、安全分级、失败处理、成本预算。**精简契约不等于删除安全约束。**

### 7.2 MA-03 示例（简版）

```yaml
mode: MA-03
purpose: 独立验证提交是否满足已写明的验收标准
when: 中高风险工程改动、原作者自测不足以独立证明
when_not: 纯文档措辞或已充分覆盖的低风险改动
roles:
  implementer: Claude Code
  verifier: Codex (独立上下文与可重现实验)
  coordinator: 按任务需要，默认无 Hermes
handoff: issue + repo + base/head SHA + 验收条款 + 测试环境与限制
exit: PASS_WITH_EVIDENCE | BLOCKED | NEEDS_MORE_EVIDENCE | ESCALATE
limits: 一次初验 + 针对修复的增量复验；继续循环需说明新增证据
source_of_truth: GitHub PR/commit + 受限执行日志
human_gate: 合并、发布、危险变更按既有授权规则
runtime_constraints: 未知结果先查询、不盲重试；禁止扩大权限
primary_skill: independent-verification (候选，未发布)
```

### 7.3 复合任务不创建复合 Skill 的原则

一次跨产品大工程可能依次触发 MA-01、MA-03、MA-02，但它们的责任范围不同：MA-01 解决方向，MA-03 解决可运行的证据，MA-02 解决变更逻辑和工程风险。最终整合任务由原项目的 Claude 或 Hermes 负责。不要另建一个“通用一站式全审 Skill”重复三个模式。

### 7.4 主 Skill 与 my-skills 的衔接

- **模式契约**（`multi-agent`）写原因、边界、角色、状态、退出和效果指标。
- **主 Skill**（`my-skills`）写调用时如何判断、步骤、输入输出、评测样例、例外处理，引用 Mode ID/版本。
- **场景画像**（`multi-agent`）写工程/研究/UI/数据的差异，不复制主 Skill 的完整方法。
- **运行适配**（Multica/驿窗/项目实现）记录自身支持版本、接口与运行证据，不把实现操作细节写死在主契约。
- **生效规则**：候选模式可先人工执行；只有 Skill 通过七站两闸且与模式契约版本兼容才标为正式；旧任务绑定原版本，不应因为主 Skill 更新而暗中更改审查标准。

## 8. 数据、反馈与真实进化

### 8.1 最小可观察事件

每次高价值运行至少留下：`run_id`、任务/项目 ID、mode ID+版本、主 Skill+版本、实际参与角色、触发与省略原因、起止时间、结果、证据链接、返工/升级与失败原因、人工介入点。**不要求把私人全文对话全部集中上传。**

当没有机器可采的数据时，标记 `unknown/not_measured`，不可为了生成好看的看板凭空补值。

### 8.2 效果指标（含单 Agent 基线）

| 观察指标 | 价值 | 注意事项 |
|---|---|---|
| 增量关键发现率 | 第二角色发现原角色忽略、且经验证重要的问题占比 | 普通措辞优化不算关键发现 |
| 缺陷逃逸率/复发率 | 工程审查和测试是否真的减少问题 | 需同风险类型比较，不能只看审查意见数 |
| 首次可接受率/返修轮数 | 是否减少反复往返 | 少返修不能以忽视缺陷为代价 |
| 完成总时长与人工触点 | 增加协同是否节约用户的精力 | 计入交接等待与上下文恢复成本 |
| 异常退出和未知状态比例 | 运行链是否可解释和恢复 | 对 Multica/驿窗链路尤为重要 |
| 模式放弃/降级比例 | 是否存在过度触发 | 停止不一定是失败，合理不启动也是成功路由 |
| 决策被推翻和后续纠正 | 思维评审是否阻止重大方向错误 | 需要可核实的复盘，不用一次经验做因果证明 |

### 8.3 持续进化闭环

`实际协作 → 事件日志 → session-retro 提案 → 将问题归因到 mode/skill/runner/source/项目 → 确认可修复的共性 → 变更模式契约或 Skill → 运行 evals/回归/安全检查 → 受控发布 → 对照旧版本效果`。

区分四类改进归属：
- 问题分类或角色不对 → **multi-agent 模式/路由修订**。
- Skill 触发条件、提示步骤或结果写法有误 → **my-skills 更新**。
- 转信、调用、幂等、会话绑定、权限或日志出错 → **驿窗 / Multica / 项目执行层**。
- 业务目标本身错误或需求改变 → **原业务/产品项目**，不反向篡改共享标准。

不因为“一次审查不满意”就改整个模式；先记录反例，回归验证是否可以复现，避免局部修复伤害其他场景。

## 9. 推荐工程结构：轻量化，不重建项目中心

```text
multi-agent/
  README.md                 # 使命、非目标、模块归属
  CURRENT.md                # 事实进度与待验证风险
  docs/roles.md             # Agent 能力与权限边界，注明版本与现实部署状态
  modes/
    MA-01-thinking-review.md
    MA-02-engineering-review.md
    MA-03-independent-verification.md
    MA-04-parallel-research.md
    MA-05-autonomous-delegation.md
    candidates/MA-06-incident-diagnosis.md
  scenarios/                # 16 个候选场景画像，允许多个引用同一个 Mode
  adapters/                 # 通用 Multica/驿窗契约或适配验证，不搬私有工作流
  evals/                    # 路由准入、退出、误触发、边界与实际效果样本
  docs/decisions/           # 重大取舍及证据
```

- 不在这里复制 `thinking-review/SKILL.md`；只保存 `Skill` 版本和真实链接。
- 不另存项目名册：以既有 `digital-twin/projects.json` 为唯一注册入口，Digiworld 只读展示。
- 不强制迁移 DT-ORC 专用实现与多年的 handoff 记录；先建关系及索引。
- 所有新角色只需先登记“职能和适用范围”，不要为每个 Agent 造一个独立长期人格和记忆数据库。

## 10. 3 批优先推进与验收

### 第一批：已验证实践模式化（P0）
1. 从现有 `thinking-review` 反推 MA-01 契约，建立**不启动**、证据暂停和成熟退出反例。
2. 选 5–10 个代表性的 Claude/Codex 与驿窗工程接力案例，形成 MA-02 与 MA-03 的触发、交接、版本证据和失败出口，而不凭空设计。
3. 制定最短路由决策卡，明确什么时候单 Agent、什么时候两个、何时绝对不加第三个。
4. 试跑 2–3 个同类型的新任务，在独立证据、返修和总人工耗时上与历史基线比较。样本不足就标待观察。

### 第二批：并行研究与 Hermes 边界（P1）
1. MA-04 在真实复杂选型/研究问题上试跑，必须留下与单路径研究相比的新证据或新选项。
2. MA-05 引用已经通过的 DT-ORC Multica 运行资料；核实 Hermes→Multica 真实集成权限、状态与失败恢复，不提前开放无人值守。
3. 将运行事件以最小标签回传到 mode/skill 的质量观察，不新增一套横向项目总控看板。

### 第三批：验证是否值得新增模式（P2）
1. 回看连续失败的真实故障，判断 MA-06 是否能比 MA-03+MA-01 明显节约返工；如不能，不立项。
2. 针对 UI、业务数据、企业任务等高频场景只增加场景画像；形成固定走法后，再由 `my-skills` 七站两闸判断是否需要独立主 Skill。
3. 选择复用价值高的通用 Multica 适配接口，**经过非 Hermes 场景真实复用**再抽取代码。

### 每批的最低验收
- 至少能回答为什么需要第二个 Agent、能解决什么单 Agent 不足。
- 可明确区分角色责任、授权主体与运行事实来源。
- 有正面案例，也有“不应该触发”的反例。
- 知道何时停止、转人工、等待事实、降回单 Agent。
- 如果没有实测效果，明示未验证而不以文件完整性宣布通过。

## 11. 最需要坚持的七个反模式禁令

1. 禁止为了可视化显示多个 Agent 就把简单任务拆成多段。
2. 禁止把“GPT 赞同”“Codex 赞同”当作独立测试证据或上线路径授权。
3. 禁止因模型数量多就以投票代替实证、证据来源和用户拍板。
4. 禁止将 Hermes 加到每次接力中做一个没有判断增量的转发节点。
5. 禁止把多 Agent 模式的正式主 Skill 复制到 `multi-agent` 或 Digiworld，形成新版本真源。
6. 禁止把 Multica 想象成能自动调度所有聊天产品；实际能否调用取决于运行环境与适配。
7. 禁止让个人与企业数字分身的身份、记忆、权限和凭据因协同方便而跨域混用。

## 12. 待检验与不在本轮直接批准的事项

- MA-02/03 的主 Skill 是否已由其他现存技能充分覆盖：需要索引和抽样，避免重复创建。
- 当前 Multica v0.8.1 支持的具体 worker 协议、任务生命周期与 Hermes M3/M4 执行证据：需实机核查，不能用已通过 M2 替代。
- 各类场景的真实成本/缺陷发现率：需按运行日志收集；本报告没有虚构数字。
- Aily 或独立外部顾问的当前安装与可用性：不凭历史角色定位自动纳入正式运行列表。
- MA-06 是否最终需要独立主 Skill：以真实排障案例验证后决定。

## 13. 最终项目级决策建议

**现在就做的**：正式定义角色能力表、MA-01～MA-05 的契约和优先级、与 `my-skills`/Multica/驿窗/Hermes 的权威边界；第一批只做现有 MA-01～03 的反向归纳与真实验证。

**暂时不做的**：大而全的自动路由平台、强制三 Agent 全流程、为每个业务场景新建一个 Skill、未经授权的 Hermes 无人值守协作、大迁仓库与统一人格记忆系统。

**长期目标**：在可核实的质量收益、时间收益和人工成本收益的支持下，逐步提高模式复用率，让用户越来越少做低价值协调，而不是让系统的角色和工作流越来越多。
