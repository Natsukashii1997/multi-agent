# 《多 Agent 协同体系 V1.0》Claude 评审（2026-11-07）

评审对象：[V1.0 原文](2026-11-07-V1.0候选全景.md)；PDF 版（21 页）第 1 页是常浩的原始提问，第 2–10 页是 ChatGPT 的聊天回答，第 11–20 页是同一回答的另一种排版，第 21 页是附件名。评审对照：常浩原始提问、已冻结的《V1.3 架构定稿》、本机真实记录。只读，没改任何项目文件。

## 0. 结论

**可以推进，但不能把 V1.0 原样作为 multi-agent 的需求基线。** 方向和原则大体正确，大部分内容与既有共识一致：默认单 Agent、模式与 Skill 分开、Hermes 只在长任务参与、不迁私有工作流、无证据不宣称。但它有三处必须先改：

1. 它不知道 multi-agent 仓库已经建好、V1.3 已冻结边界，所以第 9、13 节「现在就做 MA-01～05 五份契约 + 16 个场景文件 + adapters/」与 V1.3「不要先造五份空模板」直接冲突；
2. MA-03 默认「Codex 独立测试」不是当前实践：10-31 起 Codex 额度不足，审查已全部改走 ChatGPT；
3. MA-02 没有接上已经写好的工程审查规则和草案。这些规则彼此冲突，正是「无休止审核」的来源。

推荐做法：**不再出 V1.1 文档轮**。把 V1.0 作为「候选全景」收进 multi-agent，附本评审的修订表，然后按 V1.3 直接做执行单 I-MA-1（两份契约）。

## 2. 必须改（不改会误导后续施工）

### 2.1 与已冻结的 V1.3 和现有仓库对齐

- 事实：`multi-agent` 已在 11-07 建仓（`b49082e`，I-MA-0），名册已登记（`write_allowed=false`）。其 `CURRENT.md` 的唯一下一步是 I-MA-1：从 thinking-review 和一次真实工程审查接力各反推一份契约。V1.3 第 3.3 节原文的意思是：起步只做这两份，不要先造五份未经实战的空模板。
- V1.0 的冲突处：第 13 节「现在就做……MA-01～MA-05 的契约」；第 9 节规划 5 个 modes 文件、16 个 scenarios、adapters/、evals/。V1.0 的参考材料只列到 V1.2，没引用 V1.3。
- V1.3 第 3.1 节已定：Hermes→Multica 的适配代码归 digital-twin；只有出现两类独立消费方时，共享适配器才升格。V1.0 第 6.4 节写 multi-agent 拥有「Multica 适配约束/角色绑定接口规范」，又建了 adapters/ 目录，超出了 V1.3 的边界。
- 改法：
  - 第 13 节「现在就做」改为「I-MA-1：MA-01、MA-02 两份契约」。MA-03～05 只保留候选卡（一段话），不建文件。
  - 第 9 节删掉 adapters/ 和 scenarios/，结构以现有仓库骨架为准。
  - 头部写明「需求真源仍是 V1.3，本文是候选全景」。

### 2.2 角色表补上「底层设置」，并修正 Codex 的现状描述

- 事实：
  - V1.0 第 2.1 节说 Codex「现有工程实践中承担独立测试/验收」。本机记录显示，这只在 9–10 月成立：数码世界有大量 Codex 复核，例如 10-10「批 1 复核 358 返修交回 360」、10-11「扫描线小修 371 独立复核 373」。
  - 10-31 digital-twin 的 CURRENT 记录「Codex 额度将尽，由 Claude 正式接管」，审核方固定为 ChatGPT 聊天模式，原本等 Codex 审查的 ORC-01b-1 R7 也改由 ChatGPT 审。
  - 驿窗本机 16 单接力（11-06～07）里，15 单是工程审查或实机验收，1 单是思维评审测试，**0 单有 Codex 参与**。其中 SBX-9「反向验证」也是 ChatGPT 做的。
- 结论：MA-03「Codex 独立测试」是要**恢复**的历史做法，前提是 Codex 额度够用。现在的额度状况我没核实。
- 改法：角色表加 5 列：额度来源与紧张程度、能读到的上下文、能否真实执行、典型响应时长、是否需要常浩在场。示例：
  - ChatGPT High 读不到本机仓库，只能看送审包，不能跑测试，每轮要占常浩的 ChatGPT 额度和等待时间；
  - Codex 能在本机真实执行，但额度紧张；
  - Hermes 的大脑也用「Codex 会员」（PRD 架构图），它和 Codex 是否共用一份额度未核实，需要标出来。

  缺了这几列，「选谁」只能凭印象，没法照着做。
- 同时把聊天回答里的 6 种协作角色搬进 md，补一张「模式 × 协作角色 → 默认 Agent」矩阵。这正是常浩问的「每个场景哪些角色参与、各自定位」。

### 2.3 MA-02 接上现有工程审查规则与草案，先解决规则冲突

- 事实：工程审查是当前最高频的协同（15/16），也是「无休止审核」的主要来源。例如数码世界 #60 审了 5 轮；SBX-8 剩 2 条 P2 时，第 2 轮被拆成了一张新单。现在已有三条互相冲突的规则：
  1. agent-kit《工程流程》：同一份送审 2 轮仍不过，停下来由常浩拍板；
  2. DT-ORC ARCHITECTURE 6.4：每份最多 2 轮，L1 默认 1 轮；
  3. 驿窗工程接力：固定 2 轮，只认「通过/需修改」。

  另有一份草案 `postpane/docs/design/审核skill对接说明-2026-11-07.md`（L0–L3 风险分级、P0–P3、四档结论、续审判定、安全阀 L1 2 轮 / L2 3 轮 / L3 4 轮），没进仓库，此前约定给工程审查路径用。thinking-review 案例 C-11～C-14 也已经积累了工程类正反例。
- V1.0 第 4 节 MA-02 只写了「同一问题不无限返修」，没有分级、没有轮数、没有引用上面任何一份。
- 改法：MA-02 契约以这份草案和 C-11～C-14 为起点，第一件事是给出统一的轮数与续审规则，并写明以后由它取代上面三处说法（改动要回到 agent-kit 和驿窗同步）。

## 3. 建议改（不阻断，但影响好不好用）

### 3.1 「每个模式一个主 Skill」：推荐接受，但要常浩明确拍板

理由：数码世界的测试、数据复算、UI 验收如果各建一个 Skill，同一套独立验证方法会分裂成三个版本。my-skills 的闸 1 也要求「至少真做过两次、两次走法一致」，单个场景很难达标。这是常浩原意的工程化落法，不是缩水。但它确实改了常浩原话，应作为一条明确决定记下来。

### 3.2 模式契约与主 Skill 不要变成两份真源

thinking-review 的 SKILL.md 已经写了触发节点、角色、准入、退出、失控防护。V1.3 的 8 项契约里，「适用/禁用」「停止条件」「轮次」和 Skill 重叠。建议加一条规则：**Skill 里已有的字段，契约只写引用（文件#节），不复述。** 契约只保留 Skill 没有的内容：为什么需要这个模式、和其他模式的分界、版本绑定、效果指标、证据索引。

### 3.3 路由决策卡要说清在运行时由谁读到

第 10 节第一批第 3 条「制定最短路由决策卡」：放在 multi-agent 仓库里的文档，Claude 运行时不会读到。现在真正起路由作用的，是 thinking-review 第 1 节的检查节点和 A/B/C 分类，它已经能判断「这是 B 类，转工程审查」或「C 类，直接做」。建议：

- 不单设路由卡；
- 路由写进每个主 Skill 的准入一节（「不归我管，转 MA-xx」）；
- 全局只在 agent-kit《工程流程》留一行指引。

同时如实标注：Skill 的自动触发依赖描述匹配，可能漏触发。

### 3.4 16 个场景拆成「协同场景」和「反例」

- #15（巡检三报）、#16（日常文案、Skill 整理）的推荐方式本来就是单 Agent，它们是「不该触发」的反例，应进 evals，不进场景表；
- #13（两次修复失败）是触发条件，thinking-review 第 1 节已把它列为检查节点；
- #3、#6、#10 是「条件触发」，可以并入对应模式的适用条件。

拆完以后真正的协同场景大约 9～10 个，更诚实，也更好验证。不需要 16 份场景文件。

### 3.5 运行记录先复用现成数据，不新建日志

第 8.1 节的最小事件，对接力类模式（MA-01、MA-02）大部分已经有了：

- 驿窗 `~/Library/Application Support/app.postpane.mac/chatgpt/handoffs.json` 每单都有 id、标题（含模式前缀）、项目目录、轮次、状态、Claude 会话、ChatGPT 对话；
- agent-kit 的 `hooks/skill-usage.mjs` 已经写 `skill-usage.jsonl`。

建议先约定「标题前缀 = 模式 ID」（「思维评审｜」已是先例），用 handoffs.json 的 id 当 run_id。要新建记录，等出现驿窗覆盖不到的模式（MA-03 Codex 本机测试、MA-05）再说。

### 3.6 小处修正
