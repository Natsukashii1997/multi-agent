# 候选模式卡（MA-03～MA-06）

这四个模式还没有真实运行，或者不归本仓库推进，所以只写候选卡，不在 `modes/` 建契约，也不建 Skill（[修订表](design/2026-11-07-V1.0修订表.md) 第 8 节）。每张卡写四件事：它要解决什么，怎么组织一次试跑，凭什么晋升，下一步做什么。

晋升分两步，不能混为一谈（修订表第 6 节）：

1. **候选 → 契约**：至少有 1 次按本卡组织的真实试跑，并记进 `runs/runs.jsonl`。之后从这次试跑反推契约，放进 `modes/`。
2. **契约 → 主 Skill**：走 my-skills 七站两闸。闸 1 要求至少真做过两次、两次走法一致；闸 2 要求审计通过、盲测通过、常浩批准。

试跑前先跑 `node scripts/probe-agents.mjs`，确认要用的 Agent 可用（[agent-profile.md](agent-profile.md) 第 4 节）。

## MA-03 独立验证与测试

- **解决**：作者自测和作者同源，容易一起犯错。这个模式回答「关键行为有没有被独立证实」，产出可复现的运行证据。和 MA-02 的分界见 [MA-02 契约](../modes/MA-02-engineering-review.md) 第 2 节。
- **什么时候用**：L3 改动（权限、迁移、原子写入、长期服务）；财务模型、指标、公式要复算；功能回归需要一个不信任作者结论的人来跑。只是缺测试的，作者自己先补，不用这个模式。
- **验证方**：满足[独立性约束](agent-profile.md)即可，不绑定 Codex。可选：Codex 会话（独立 worktree）；隔离容器复跑；不带作者上下文的新 Claude 会话。
- **试跑怎么做**：
  1. 作者写验证目标：要证实哪几个行为、正例和反例各是什么、通过标准是什么。不写自己预期的结果。
  2. 验证方只拿到目标、分支或提交号、运行方式，自己执行，留下命令和原样输出。
  3. 作者对照结果：发现了新缺陷就修，修完由验证方复跑一次。
  4. 往 `runs/runs.jsonl` 记一条：`mode` 写 `MA-03`；`baseline` 写作者自测做到哪一步（测试数、结果）；`verified_findings` 写验证方发现、经作者复现确认、作者自测没发现的缺陷数（还没确认的写 null）；`evidence` 写验证环境和命令输出所在位置；同一任务还走了 MA-02 的，两条记录用同一个 `case_id`。
- **晋升条件**（两次试跑满足其一，才进入闸 1 讨论）：
  - 至少一次 `verified_findings` ≥ 1，且其中有 P0/P1；
  - 或者证实了作者自己证实不了的行为。这一条要同时写明：作者为什么证实不了（例如作者环境有残留状态）、验证环境是什么、证据在哪里，并由常浩确认算数。

  两次都一无所获，就把它定为 MA-02 里的一档验证深度，不做独立 Skill。
- **依赖**：Codex 和 Hermes 是同一个 ChatGPT Plus 账号（2026-11-08 核实），推断共用一份额度。用 Codex 当验证方要避开 Hermes 夜跑。
- **下一步**：批 B 第一次试跑，并进一个真实的 L2/L3 工程任务，由验证方提供 MA-02 审查要的运行证据。这样一个任务的产出，同时算 MA-02 的一次运行和 MA-03 的首跑。

## MA-04 并行研究与方案综合

- **解决**：只沿一条路线研究，遗漏了备选或证据。这个模式让几个研究方各自独立探索，再由一个角色比较证据，综合出结论。
- **什么时候用**：有真实取舍的多个技术或产品方案；重要信息依赖外部证据的研究、竞品、选型。答案在仓库里就能查到的，不用这个模式。
- **试跑怎么做**：
  1. 发起者按假设或路线拆出 2～3 个研究题，定好统一的比较指标和来源要求。
  2. 各研究方互不可见，各自出报告，每条结论附来源。
  3. 由一个综合者合并：冲突的证据标出来并取证，按统一指标比较，给出建议。
  4. **对照组**：同一个问题再让单 Agent 做一遍。对照组在看到并行研究结果之前完成，报告单独存档。
  5. 记进 `runs/runs.jsonl`：`baseline` 写对照组报告的位置；`changed_decision` 写最终选择是否因并行研究而改变；`evidence` 写各研究方报告和综合报告的位置。
- **晋升条件**：两次试跑里，至少一次 `changed_decision` 为 true，并且能指出是哪条证据改变了选择、这条证据对照组报告里没有。「改变了选择」由常浩确认。都没有，就保留为 MA-01 的取证手段，不建 Skill。
- **下一步**：批 B，等出现一个真实的多方案选型问题时试跑。不为了试跑去编题目。

## MA-05 长期任务委派

- **归属**：Hermes 控制面、派单、授权、Multica 实施都归 digital-twin（DT-ORC）（修订表第 5 节）。本仓库只在 digital-twin 验证跑通后，提炼可复用的委派方法。
- **现状**：DT-ORC M5 夜跑正在 digital-twin 推进（驿窗 `h1a1b894e96600` 等）。不宣称已经自治。
- **晋升条件**：digital-twin 里至少两条长期任务完成了完整的「授权 → 派单 → 执行 → 验收 → 汇报」，并且有一次中断后成功恢复。满足后，再判断有没有可以脱离 Hermes、Multica 实现的通用方法值得写成 `autonomous-delegation`。
- **下一步**：本仓库不动，跟着 digital-twin 的 CURRENT 走。

## MA-06 疑难故障根因会诊

- **定位**：先不当独立模式，定义成组合用法：MA-01 让独立一方构建不同的根因假设，MA-03 用可证伪的实验排除错误假设。
- **什么时候用**：同一故障修过两次还复发；问题长期无法复现；几个技术假设相互冲突。
- **晋升条件**：攒到 3 个以上典型案例，并且有案例证明「MA-01 + MA-03 组合」解决不了时，才考虑单独立项。
- **下一步**：出现案例就记进 `runs/runs.jsonl`，`mode` 写 `MA-06`。
